# 注释与文档规范

本文件规定注释、文档与代码写法的最小约定，是评审与自查的依据。
构建与持续集成见 [构建文档](BUILD.md)，运行与操作见 [使用说明](USAGE.md)，
棋盘规则见 [棋盘规则](RULES.md)，存档字段见 [存档格式](SAVE_FORMAT.md)。

## 1. 四条基本立场

1. **注释解释"为什么"、"有什么约束"、"哪里有坑"，不解释"代码在做什么"。**
   能一眼看懂的语句不加注释；需要三行以上才能说清的行为，上升到函数级注释。
2. **同一事实只写一处。** 数字、清单、默认值都有唯一权威位置（见 §5），
   其他位置只写链接或数量级。复制粘贴是文档漂移的主要来源。
3. **注释必须可验证。** 写"保证每方编号唯一"可以，写"逻辑比较健壮"不行；
   前者能对着 `core::validate_state` 检查，后者只能猜。
4. **面向人的文字用中文，机器标识用英文。** 具体边界见 §4。

## 2. 注释分层与语法

| 层级     | 位置                                  | 语法            | 强度 | 写什么                                             |
| -------- | ------------------------------------- | --------------- | ---- | -------------------------------------------------- |
| 文件头   | 每个 `.h` / `.cpp` 顶部               | `///` + `@file` | 必须 | 职责、不变量、前置条件、线程与异常约定             |
| 脚本头   | 每个 `CMakeLists.txt` / `.cmake` 首行 | `#`             | 必须 | 该文件负责什么；不写 `@file`（Doxygen 不读 CMake） |
| 公共 API | 头文件中的类型、函数、枚举、常量      | `///` + Doxygen | 必须 | 语义、参数、返回值、抛什么、何时非法               |
| 实现分节 | `.cpp` 内部                           | `//`            | 建议 | 分步意图、算法选择、被否决的替代方案               |
| 行内     | 关键行上一行或行尾                    | `//`、`///<`    | 按需 | 单位、边界、非显然的常量来源                       |

**语法规定：**

- 只用 `///` 与 `//`，**禁用 `/** ... */`**：块注释与行注释混排会割裂视觉，
也让"文件头必须匹配 `^/// @file`"的校验脚本失效。
- `///<` 只用于成员、枚举值与常量的行尾说明，不用于普通语句。
- 注释与代码之间不留空行；一组注释与它说明的代码之间不留空行。
- 注释不写"以下代码""这里""如上所述"这类依赖上下文的指代，要能单独读懂。

### 2.1 行上还是行尾

| 注释描述的对象                            | 位置               | 理由                                           |
| ----------------------------------------- | ------------------ | ---------------------------------------------- |
| 类型成员、枚举值、常量                    | 行尾 `///<`        | Doxygen 成员文档的语法要求；声明表保持一行一项 |
| 测试夹具表中的单行数据（`put(...)` 这类） | 行尾 `//`          | 标签属于该行数据，拆到上一行会让表格失去对照   |
| 结构边界：`}  // namespace X`             | 行尾，必须写全名称 | 收尾标记，不是解释；写全名称才能被检索         |
| 一段语句、一个决定、一条理由              | 独立一行 `//`      | 常需多句，且要与代码分开演进                   |

- 除上表四类，行尾不写注释；其余注释一律写在语句的上一行。
- 头文件使用 `#pragma once`，不写 include guard 与 `#endif` 注释。
- 行尾注释只允许一句短语；预计会被列宽折断的，直接改行上。
- 句末用中文句号；需要两句以上时本来就不该放行尾。

### 2.2 空行

- 文件头块后空一行写 `#pragma once`，再空一行写 `#include`。
- 一条注释连同它说明的语句算一段；段与段之间空一行，注释与语句之间不空行。
- 函数体第一行与 `}` 之前不空行；命名空间内容前后各空一行。
- 连续空行只允许一个。

## 3. 文件头模板

文件头是"这个文件为什么存在"的唯一入口，六行以内能说清就不要写十行。

### 3.1 头文件

文件头放在文件最前面，`#include` 之前，块后空一行：读者打开文件先知道"这是什么"，
再面对一长串包含；clang-format 只重排包含块，也不会把它当成某条包含的附属注释。

```cpp
/// @file src/core/rules.h
/// @brief 走子合法性与掷骰后的选子规则。
///
/// 职责：判定"能不能走""能选哪些子"，不修改局面（结算在 game.h）。
/// 不变量：check_move 返回空串 ⟺ 该走法合法；选子结果数量不超过 2。
/// 前置：传入的 state 已通过 core::validate_state。
/// 异常：不抛；非法输入以空串或中文原因表达。
/// 线程：无可变全局状态，可并发调用。
```

`@file` 必须写**相对仓库根**的路径且与真实文件名一致（`src/core/rules.h`，不是 `rules.h`），
并且必须是文件第 1 行，这样脚本既能核对路径，也能确认文件头没有被挪到 `#include` 之后。

文件头块之后写 `#pragma once`，不写 `#ifndef`/`#define`/`#endif`：唯一宏名与文件尾收尾标记都不再需要维护。

### 3.2 实现文件

```cpp
/// @file src/core/rules.cpp
/// @brief rules.h 的实现。
///
/// 关键约定：方向表按 (行增, 列增) 定义；Side::None 不做方向拦截，
/// 作为防御性默认，正常流程不会走到。
```

实现文件不重复头文件中已写明的异常与线程约定；两处冲突时以头文件为准。

### 3.3 CMake 与脚本

```cmake
# 测试注册表：全仓库测试清单、标签、超时的唯一事实源。
# 文档中出现的用例数量一律以此文件为准，不在别处重复维护。
```

CMake 没有 Doxygen，脚本头只写 `#` 说明，不加 `@file` 标记；"必须有文件头"与其他文件相同。
注释里同样禁止 `BUG-xx`、`P0-x` 与"旧实现"式历史叙事。

### 3.4 测试文件

```cpp
/// @file tests/core_rules_test.cpp
/// @brief 校验走子方向、选子降级与胜负判定。
///
/// 回归背景：见 `#board-remainder-click`。
```

"回归背景"只在确有台账条目时写，锚点必须能在 `docs/HISTORY.md` 找到同名标题；没有条目就删掉这一行。
**不允许出现 `BUG-xx`、`P0-x` 这类无出处编号**（见 §6）。

**禁止出现在文件头的字段：** `@author`、`@date`、`@version`、`@copyright`。
作者与时间由 git 记录，版本由 CMake 的 `PROJECT_VERSION` 记录，许可证由 `LICENSE` 记录。

## 4. 语言、术语与文案

### 4.1 中文的边界

**必须用中文：** 注释、Markdown 文档、异常 `what()`、日志与 `qDebug`、界面文字、
CLI 提示、benchmark 输出中的说明性文字。

**保持英文：** 变量/函数/类型名、文件名与目录名、JSON 字段名（`requests`、`x0`、`color`）、
CMake 目标名与测试名（`core_rules`、`cli_eof`）、第三方库原文
（nlohmann 的 `e.what()`、SQLite 的 `sqlite3_errmsg`，可原文附在中文句子后面）。

**三类例外（保持原样）：**

1. 品牌与装饰文案：主菜单副标题 `Einstein Chess`、页脚 `Made for C++ Course`。
2. benchmark 的局面键与统计列名：`opening`、`fallback`、`midgame`、`endgame`、`p95`。
   它们与 `benchmarks/ai_benchmark.cpp` 的构造函数名和 BENCHMARK.md 表格的行键一致，
   保留英文才方便按这些词检索；表格的中文列名（中位数、最小值、最大值）不受此例外影响。
3. 第三方库的错误原文（见上）。

**Botzone 的 stderr 前缀同样用中文**（如"协议错误：""内部错误："）。平台不解析 stderr，
中文不影响判题；中文在未知 locale 的容器里可能显示为乱码，这只影响人工排查。

### 4.2 术语表

| 术语                  | 用法                          | 不要写成          |
| --------------------- | ----------------------------- | ----------------- |
| `Level`               | 档位（界面显示"强度"）        | 版本、代          |
| `Random` / `Search`   | 随机档 / 搜索档               | 简单 AI / 复杂 AI |
| ply                   | 手（一次落子）                | 层、步、回合      |
| turn                  | 回合（一次掷骰 + 随后的走子） | 轮、手            |
| `GameState`           | 局面                          | 状态、棋盘、场景  |
| 竞速表项              | 状态                          | 局面、节点        |
| 存档                  | save 记录（含名字与时间戳）   | 文件、档          |
| 槽位                  | 存档名                        | 位置、编号        |
| layout                | 布阵（每方棋子的编号排列）    | 布局、阵型        |

同一段文字里不要混用"手"和"回合"；`SearchConfig::max_depth` 一律按"手"解释。

### 4.3 文案规则

- 异常说清三件事：**哪一步失败 + 为什么 + 关键值**。例：
  `"反序列化失败: 棋盘格 (3, 4) 溢出 32 位整数"` 能定位到字段并说明原因，
  只写 `"数据损坏"` 没有信息量；调用方已经用标题或前缀写明步骤时，消息里不再重复同一句话。
- 不用感叹号与英文缩写（`err`、`invalid`）；带感叹号的提示
  （如"现在不能扔骰子！"）应写成陈述句。
- 表情只出现在 GUI 面向玩家的状态文字与 README 的章节标题里；异常消息、日志、CLI 与 Botzone 的输出、代码注释与其他 docs 一律不用表情。
- 面向用户的提示不出现内部编号、函数名、数据库字段名。
- 数字带单位：`23.98 ms`、`4 手`、`第 3 格`。
- 统一中文全角标点；半角标点只用于代码标识符内部。

异常类型按“失败来源”选，不要一律用 `std::invalid_argument`：

| 判据 | 类型 | 典型场景 |
|---|---|---|
| 参数值不合法（含传入的局面、枚举、字符串） | `std::invalid_argument` | `decide_move` 收到非思考阶段、`save_game` 收到不自洽局面 |
| 对象自身状态不允许该调用 | `std::logic_error` | 布阵阶段掷骰、重复提交布阵 |
| 下标或坐标越界 | `std::out_of_range` | `Board::at` |
| 外部数据或环境在运行期才失败 | `std::runtime_error` | 存档串损坏、数据库打不开 |
| 外部协议输入不合法 | `ProtocolError`（继承 `std::runtime_error`） | Botzone 请求缺字段 |

`std::invalid_argument` 已继承 `std::logic_error`，两者都表示调用方的 bug；不要直接抛 `std::exception`。
`@throws` 写清类型，测试按类型断言，而不是只断言“抛了异常”。

### 4.4 链接写法

链接文字必须说明目标是什么，只写文件名等于让读者盲点：

- 正确：`[构建文档](BUILD.md)`、`[设计取舍](DESIGN.md)`、`[使用说明](USAGE.md)`。
- 错误：`[BUILD.md](BUILD.md)`、`[这里](BUILD.md)`、`[点击查看](BUILD.md)`。

同一段落重复引用同一目标时，第二次可以用简称（如"上文的构建文档"），但仍不能只写文件名。
指向文件的链接一律用相对路径；链接目标必须真实存在，否则按 §6 处理。

## 5. 单一事实源

| 事实                       | 唯一权威位置                                 | 其他位置怎么写                       |
| -------------------------- | -------------------------------------------- | ------------------------------------ |
| 测试清单、数量、标签、超时 | `tests/CMakeLists.txt`                       | 写"全部用例见 tests/CMakeLists.txt"；README 与 BUILD 里的总数由 check_repo 核对 |
| AI 档位定义与默认档        | `src/ai/ai.h`                                | 只写档位名，不抄默认值               |
| GUI 三段过渡延迟           | `game_widget.h` 的默认参数                   | 只写"见 game_widget.h"               |
| 棋盘规则与判定顺序         | `src/core/rules.cpp` + `core_rules_test.cpp` | 一句话摘要 + 链接到 `RULES.md`       |
| 存档字段与失败模式         | `src/storage/save_manager.h` 的格式说明      | 一句话摘要 + 链接到 `SAVE_FORMAT.md` |
| 随机源的种子与已掷次数     | `core::Game` 的 `seed()` / `roll_count()`    | 只写“随机流随存档记录”，不抄字段值   |
| 模块分层与状态机           | `docs/ARCHITECTURE.md`                       | 只写模块名，不抄依赖表               |
| 已修复缺陷与回归           | `docs/HISTORY.md` 的锚点                     | 只写锚点链接，不复述根因             |
| 构建方式与 CI job          | `.github/workflows/ci.yml` + `BUILD.md`      | 只写命令，不抄 job 细节              |
| 性能数字                   | `docs/BENCHMARK.md`                          | 只写数量级                           |
| 版本号                     | 根 `CMakeLists.txt` 的 `PROJECT_VERSION`     | 界面经 `EINSTEIN_VERSION` 读取       |

三条硬规则：

1. 文档里的数字必须带**口径**（"p95 取重复样本中的最坏值"），否则无法判断可比性。
2. 引用清单时写"见 X"，不复制表格。
3. 新增事实类别时，先在本表登记权威位置，再动笔。

## 6. 禁止项

### 6.1 判定标准

一句话是否合格，先问三个问题，任一为"是"即不合格：

1. 它是否在描述"某个东西过去是什么样"（含用"改""不再""曾""原""旧""新"表达的状态变化）？
2. 它是否包含没有触发条件的时间词？
3. 它是否用形容词代替了可验证的条件？

解释"为什么不用另一种写法"不属于历史叙事，判据是句子是否声称"先前采用另一种做法"。
允许：「这里用 `std::from_chars`，因为流提取遇到溢出会置 `failbit`，会被误判成数据缺失。」
禁止：方向相反、声称"先前用的是另一种做法"的句子。

### 6.2 禁词表

| 类别                     | 例词                                                       | 替代写法                               |
| ------------------------ | ---------------------------------------------------------- | -------------------------------------- |
| 指代过去的版本或实现     | 旧实现、旧版本、原实现、曾经的、早期、历史遗留、迁移、废弃 | 只写当前契约；背景进 HISTORY.md        |
| 描述状态变化             | 改、改为、改成、不再、换成、替换为、升级为、已经不支持     | 直接写当前行为                         |
| 无触发条件的时间词       | 目前、暂时、以后可以、先这样、暂时保留                     | 写清条件与触发时机，或删               |
| 无出处编号               | `BUG-xx`、`P0-x`                                           | 链接 HISTORY.md 锚点，或删编号只写现象 |
| 无编号的待办             | `TODO`、`FIXME`                                            | `TODO(#123)` 或删除                    |
| 未经校验的数字           | 散落在文档里的用例数、默认延迟等副本                       | 链接事实源；脚本校验过的用例数与 BENCHMARK 的测量值除外 |
| 不可验证的评价           | 逻辑健壮、性能很好、应该没问题                             | 可检查的条件或测得的数字               |
| 复述代码                 | `++i // 自增`                                              | 删，或写"为什么是 i 不是 j"            |
| 失效的 Markdown 相对链接 | —                                                          | 提交前点开；CI 脚本校验                |

## 7. 示例

### 7.1 好注释的三个特征

- 解释取舍：`ai.cpp` 只保存种子、每次决策按“种子 + 局面”现构造引擎，注释说明
  为什么不能留着上一次的引擎状态——读档后要走回与存档前相同的棋，而存档里没有
  AI 的内部状态。
- 解释陷阱：`save_manager.cpp` 的尾部解析必须用 `std::from_chars`，因为流提取遇到
  溢出会置 `failbit`，会被误判成"数据缺失"。
- 解释职责边界：`main_botzone.cpp` 文件头说明本文件只管 stdin/stdout 与异常兜底，
  协议逻辑在库里以便单测。
- 写得出验证方式：`board_widget.h` 曾写着"控件不保留任何跨帧的中间状态"，而类里有
  四个缓存成员；这种能被代码直接推翻的判断，要么删掉，要么写成真正的不变量。

共同点：删掉注释后，读者会做出错误的修改。这才是注释的价值。

### 7.2 反例不进仓库

反例逐条归档会随时间过期，还要跟着代码一起维护。本规范只留判据：注释必须能被当前
代码验证，写不出验证方式就删掉。

## 8. 落地与校验

### 8.1 落地节奏

- 新增文件立即遵守；其余文件按模块分批补齐，一个模块一次提交。
- 一次提交只做一类内容：注释、文案、文档不混合，这样 `git diff` 可以只按注释行过滤来审查。

### 8.2 校验项

| 条款或检查项                                                     | 方式                              |
| ---------------------------------------------------------------- | --------------------------------- |
| §2 禁 `/** */`；`@file` 在第 1 行且路径一致；无 `@author` 等字段 | `cmake -P tools/check_repo.cmake` |
| §2 脚本头：`CMakeLists.txt` / `.cmake` 首行是 `#` 注释           | `cmake -P tools/check_repo.cmake` |
| §2 头文件保护统一用 `#pragma once`                                | `cmake -P tools/check_repo.cmake` |
| §2 文本卫生：无 BOM、无 CRLF、无制表符与行尾空白                  | `cmake -P tools/check_repo.cmake` |
| §3.4 回归锚点在 `docs/HISTORY.md` 有同名标题                     | `cmake -P tools/check_repo.cmake` |
| §4.4 链接文字不是目标文件名本身                                  | `cmake -P tools/check_repo.cmake` |
| §6.2 禁词表零命中（含 `docs/*.md` 与 README）                    | `cmake -P tools/check_repo.cmake` |
| Markdown 相对链接可达                                            | `cmake -P tools/check_repo.cmake` |
| 文档中的测试数量与 `tests/CMakeLists.txt` 一致                   | `cmake -P tools/check_repo.cmake` |
| C++ 每行 100 列、文件末尾有换行                                  | `clang-format --dry-run --Werror` |
| §2.1 行尾四类、§2.2 空行、§3 文件头内容、§4.1–§4.3 的语言与文案、§4.2 术语、§5 其余数字规则、§9 的行为约定 | 人工评审 |

脚本只守住能机械判定的部分；表里标“人工评审”的条款不会因为跑过脚本就算通过，按 §8.3 逐条看。
检查脚本只依赖 CMake 本身，本地与 CI 跑的是同一条命令；提交前在仓库根执行即可，报错会带上文件与行号。

### 8.3 评审清单

- [ ] 提交前跑过 `cmake -P tools/check_repo.cmake`
- [ ] `clang-format --dry-run --Werror` 无差异
- [ ] 新文件有 `@file`，内容与文件名一致
- [ ] 新增的 CMake 脚本首行写了职责
- [ ] 公共函数写了 `@param` 与 `@throws`（抛异常的函数）

## 9. 代码写法的硬约定

注释之外，下列写法同样影响可读性。新增代码必须遵守，存量按模块逐步对齐。

1. 命名空间等于模块目录名：`core`、`ai`、`storage`、`cli`、`gui`、`botzone`；测试辅助用 `test_support`。
2. 棋盘边长与每方棋子数只引用 `core::Board::kSize` / `kChessCount`；`src/` 里需要 `int` 时在本文件派生一个 `constexpr`，不写裸的数字。
3. 容器与棋盘的遍历索引用 `std::size_t`；参与像素扣减、可能为负的算术用 `int`，跨界转换写 `static_cast`。
4. 类型名写全（`std::size_t`、`std::array`），不写裸 `size_t`，也不写 `using namespace`。
5. Qt 字符串字面量用 `QStringLiteral`；`const char*` 转 `QString` 走 `QString::fromUtf8`，不使用隐式转换。
6. 每个对象在声明处完成初始化：标量、指针与无构造函数的聚合必须带初值（`{}`、`{值}`、`= nullptr`）；类类型由构造函数建立不变量，不写多余的 `{}`。声明时确实没有有意义的初值时，改用 `std::optional` 或把声明推迟到能初始化它的位置，不拿 `0` 或空串占位。
7. 只读查询标 `[[nodiscard]]`，包括返回 `bool`、枚举、容器的 getter。
8. 每个文件末尾保留一个换行，由 `.clang-format` 的 `InsertNewlineAtEOF` 保证。
9. 异常类型按 §4.3；消息写失败点与原因，调用方已在标题或前缀里写明同一步骤时不再重复那句话（GUI 的“保存失败”标题下，消息不以“保存失败: ”开头）。
10. 枚举 `switch` 覆盖全部枚举值时不写 `default`，让编译器报出新增值；确实需要兜底值时才写 `default`，并在注释说明兜底语义。
11. Qt 信号连接：需要访问成员状态、会被多处复用的槽写 `private slots:`；只在连接点用一次的转发逻辑用 lambda。
12. 只读且不保存引用的字符串参数用 `std::string_view`；需要保存引用或转交所有权的用 `const std::string&` 或 `std::string`。
13. C++ 源码每行不超过 100 列（clang-format 统一处理）；CMake 不设硬上限，但控制在 120 列以内，避免横向滚动。不手动拆分表达式来折行；一行太长时改变量名或提前提取中间结果，折行位置交给 clang-format。
14. 解析函数用返回值表达失败：能失败的函数返回 `std::optional`，不抛出、也不通过出参回传；菜单编号按 1 起算，函数名用 `number`，调用方取下标时显式减一。
15. `auto`：能从初始化器直接看出类型、且不隐藏关键信息时用 `auto`（迭代器、`static_cast` 的结果、容器元素、结构化绑定）；公开接口、需要区分 `std::size_t` 与 `int` 的边界处写全类型。
16. 自增/自减一律前置（`++i`）；确实需要后置值时拆成两行，先保存旧值再自增。
17. 不用 C 风格转换，按用途选 `static_cast` / `reinterpret_cast`；只在包装 C API 的最小范围内例外，当前只有 `sqlite_wrapper.cpp` 对 `sqlite3*` / `sqlite3_stmt*` 的转换。
