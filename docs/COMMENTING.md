# 注释与文档规范

本文件规定注释与文档的写法，是评审与自查的依据。
构建与持续集成见 [构建文档](BUILD.md)，运行与操作见 [使用说明](USAGE.md)，
棋盘规则见 [棋盘规则](RULES.md)，存档字段见 [存档格式](SAVE_FORMAT.md)。

## 1. 四条基本立场

1. **注释解释"为什么"、"有什么约束"、"哪里有坑"，不解释"代码在做什么"。**
   能一眼看懂的语句不加注释；需要三行以上才能说清的行为，上升到函数级注释。
2. **同一事实只写一处。** 数字、清单、默认值都有唯一权威位置（见 §5），
   其他位置只写链接或数量级。复制粘贴是文档漂移的主要来源。
3. **注释必须可验证。** 写"保证每方编号唯一"可以，写"逻辑比较健壮"不行；
   前者能对着 `core::validate_state` 检查，后者只能猜。
4. **面向人的文字用中文，机器标识用英文。** 具体边界见 §4。

## 2. 注释分层与语法

| 层级 | 位置 | 语法 | 强度 | 写什么 |
| --- | --- | --- | --- | --- |
| 文件头 | 每个 `.h` / `.cpp` / `.cmake` 顶部 | `///` + `@file` | 必须 | 职责、不变量、前置条件、线程与异常约定 |
| 公共 API | 头文件中的类型、函数、枚举、常量 | `///` + Doxygen | 必须 | 语义、参数、返回值、抛什么、何时非法 |
| 实现分节 | `.cpp` 内部 | `//` | 建议 | 分步意图、算法选择、被否决的替代方案 |
| 行内 | 关键行上一行或行尾 | `//`、`///<` | 按需 | 单位、边界、非显然的常量来源 |

**语法规定：**

- 只用 `///` 与 `//`，**禁用 `/** ... */`**：块注释与行注释混排会割裂视觉，
  也让"文件头必须匹配 `^/// @file`"的校验脚本失效。
- `///<` 只用于枚举值与结构体字段的行尾说明，不用于普通语句。
- 注释与代码之间不留空行；一组注释与它说明的代码之间不留空行。
- 注释不写"以下代码""这里""如上所述"这类依赖上下文的指代，要能单独读懂。

## 3. 文件头模板

文件头是"这个文件为什么存在"的唯一入口，六行以内能说清就不要写十行。

### 3.1 头文件

```cpp
/// @file core/rules.h
/// @brief 走子合法性与掷骰后的选子规则。
///
/// 职责：判定"能不能走""能选哪些子"，不修改局面（结算在 game.h）。
/// 不变量：check_move 返回空串 ⟺ 该走法合法；选子结果数量不超过 2。
/// 前置：传入的 state 已通过 core::validate_state。
/// 异常：不抛；非法输入以空串或中文原因表达。
/// 线程：无可变全局状态，可并发调用。
```

`@file` 必须写**相对仓库根**的路径且与真实文件名一致（`core/rules.h`，不是 `rules.h`），
这样脚本可以直接查文件是否存在。

### 3.2 实现文件

```cpp
/// @file core/rules.cpp
/// @brief rules.h 的实现。
///
/// 关键约定：方向表按 (行增, 列增) 定义；Side::None 不做方向拦截，
/// 作为防御性默认，正常流程不会走到。
```

实现文件不重复头文件中已写明的异常与线程约定；两处冲突时以头文件为准。

### 3.3 CMake 与脚本

```cmake
# 测试注册表：全仓库测试清单、标签、超时的唯一事实源。
# 文档中出现的用例数量一律以此文件为准，不在别处重复维护。
```

### 3.4 测试文件

```cpp
/// @file core_rules_test.cpp
/// @brief 校验走子方向、选子降级与胜负判定。
///
/// 回归背景：见 docs/HISTORY.md#board-remainder-click。
```

"回归背景"只在确有台账条目时写，锚点必须能跳转；没有条目就删掉这一行。
**不允许出现 `BUG-xx`、`P0-x` 这类无出处编号**（见 §6）。

**禁止出现在文件头的字段：** `@author`、`@date`、`@version`、`@copyright`。
作者与时间由 git 记录，版本由 CMake 的 `PROJECT_VERSION` 记录，许可证由 `LICENSE` 记录。

## 4. 语言、术语与文案

### 4.1 中文的边界

**必须用中文：** 注释、Markdown 文档、异常 `what()`、日志与 `qDebug`、界面文字、
CLI 提示、benchmark 输出中的说明性文字。

**保持英文：** 变量/函数/类型名、文件名与目录名、JSON 字段名（`requests`、`x0`、`color`）、
CMake 目标名与测试名（`core_rules`、`cli_eof`）、第三方库原文
（nlohmann 的 `e.what()`、SQLite 的 `sqlite3_errmsg`，可原文附在中文句子后面）。

**三类例外（保持原样）：**

1. 品牌与装饰文案：主菜单副标题 `Einstein Chess`、页脚 `Made for C++ Course`。
2. benchmark 的场景键与统计列名：`opening`、`fallback`、`midgame`、`endgame`、
   `median`、`p95`——它们同时是 BENCHMARK.md 表格的行键与复现命令的检索词。
3. 第三方库的错误原文（见上）。

**Botzone 的 stderr 前缀同样用中文**（如"协议错误：""内部错误："）。平台不解析 stderr，
中文不影响判题；中文在未知 locale 的容器里可能显示为乱码，这只影响人工排查。

### 4.2 术语表

| 术语 | 用法 | 不要写成 |
| --- | --- | --- |
| `Level` | 档位（界面显示"强度"） | 版本、代 |
| `kRandom` / `kSearch` | 随机档 / 搜索档 | 简单 AI / 复杂 AI |
| ply | 手（一次落子） | 层、步、回合 |
| turn | 回合（一次掷骰 + 随后的走子） | 轮、手 |
| `GameState` | 局面 | 状态、棋盘、场景 |
| 竞速表项 | 状态 | 局面、节点 |
| 存档 | save 记录（含名字与时间戳） | 文件、档 |
| 槽位 | 存档名 | 位置、编号 |
| layout | 布阵（6 枚棋子的编号排列） | 布局、阵型 |

同一段文字里不要混用"手"和"回合"；`SearchConfig::max_depth` 一律按"手"解释。

### 4.3 文案规则

- 异常说清三件事：**哪一步失败 + 为什么 + 关键值**。例：`"保存失败: AI 档位非法: 7"`，
  而不是 `"保存失败"`。
- 不用感叹号、表情、英文缩写（`err`、`invalid`）。带感叹号的提示
  （如"现在不能扔骰子！"）应写成陈述句。
- 面向用户的提示不出现内部编号、函数名、数据库字段名。
- 数字带单位：`23.98 ms`、`4 手`、`第 3 格`。
- 统一中文全角标点；半角标点只用于代码标识符内部。

### 4.4 链接写法

链接文字必须说明目标是什么，只写文件名等于让读者盲点：

- 正确：`[构建文档](BUILD.md)`、`[设计取舍](DESIGN.md)`、`[使用说明与当前限制](../README.md)`。
- 错误：`[BUILD.md](BUILD.md)`、`[这里](BUILD.md)`、`[点击查看](BUILD.md)`。

同一段落重复引用同一目标时，第二次可以用简称（如"上文的构建文档"），但仍不能只写文件名。
指向文件的链接一律用相对路径；链接目标必须真实存在，否则按 §6 处理。

## 5. 单一事实源

| 事实 | 唯一权威位置 | 其他位置怎么写 |
| --- | --- | --- |
| 测试清单、数量、标签、超时 | `tests/CMakeLists.txt` | "19 个用例，见 tests/CMakeLists.txt" |
| AI 档位定义与默认档 | `src/ai/ai.h` | 只写档位名，不抄默认值 |
| GUI 三段延迟 400/500/800 | `game_widget.h` 的默认参数 | "见 game_widget.h" |
| 棋盘规则与判定顺序 | `src/core/rules.cpp` + `core_rules_test.cpp` | 一句话摘要 + 链接到 `RULES.md` |
| 存档字段与失败模式 | `src/storage/save_manager.h` 的格式说明 | 一句话摘要 + 链接到 `SAVE_FORMAT.md` |
| 模块分层与状态机 | `docs/ARCHITECTURE.md` | 只写模块名，不抄依赖表 |
| 已修复缺陷与回归 | `docs/HISTORY.md` 的锚点 | 只写锚点链接，不复述根因 |
| 构建方式与 CI job | `.github/workflows/ci.yml` + `BUILD.md` | 只写命令，不抄 job 细节 |
| 性能数字 | `docs/BENCHMARK.md` | 只写数量级 |
| 版本号 | 根 `CMakeLists.txt` 的 `PROJECT_VERSION` | 界面经 `EINSTEIN_VERSION` 读取 |

三条硬规则：

1. 文档里的数字必须带**口径**（"p95 取 20 次重复中的最坏值"），否则无法判断可比性。
2. 引用清单时写"见 X"，不复制表格。
3. 新增事实类别时，先在本表登记权威位置，再动笔。

## 6. 禁止项

### 6.1 判定标准

一句话是否合格，先问三个问题，任一为"是"即不合格：

1. 它是否在描述"某个东西过去是什么样"（含用"改""不再""曾""原""旧""新"表达的状态变化）？
2. 它是否包含没有触发条件的时间词？
3. 它是否用形容词代替了可验证的条件？

解释"为什么不用另一种写法"不属于历史叙事，判据是句子是否声称"先前采用另一种做法"。
允许：「这里用 `std::from_chars`，因为流提取遇到溢出会置 `failbit`，会被误判成数据缺失。」
禁止：方向相反、声称"先前用的是另一种做法"的句子。

### 6.2 禁词表

| 类别 | 例词 | 替代写法 |
| --- | --- | --- |
| 指代过去的版本或实现 | 旧实现、旧版本、原实现、曾经的、早期、历史遗留、迁移、废弃 | 只写当前契约；背景进 HISTORY.md |
| 描述状态变化 | 改、改为、改成、不再、换成、替换为、升级为、已经不支持 | 直接写当前行为 |
| 无触发条件的时间词 | 目前、暂时、以后可以、先这样、暂时保留 | 写清条件与触发时机，或删 |
| 无出处编号 | `BUG-xx`、`P0-x` | 链接 HISTORY.md 锚点，或删编号只写现象 |
| 无编号的待办 | `TODO`、`FIXME` | `TODO(#123)` 或删除 |
| 复制的数字 | 19、5、14、400/500/800 | 链接事实源 |
| 不可验证的评价 | 逻辑健壮、性能很好、应该没问题 | 可检查的条件或测得的数字 |
| 复述代码 | `++i // 自增` | 删，或写"为什么是 i 不是 j" |
| 失效的 Markdown 相对链接 | — | 提交前点开；CI 脚本校验 |

## 7. 示例

### 7.1 好注释的三个特征

- 解释取舍：`ai.cpp` 的随机数引擎用 `thread_local`，注释把两个约束写在一起——
  每线程独立、不与其他线程共享状态；固定种子后同一线程内的序列可复现。
- 解释陷阱：`save_manager.cpp` 的尾部解析必须用 `std::from_chars`，因为流提取遇到
  溢出会置 `failbit`，会被误判成"数据缺失"。
- 解释职责边界：`main_botzone.cpp` 文件头说明本文件只管 stdin/stdout 与异常兜底，
  协议逻辑在库里以便单测。

共同点：删掉注释后，读者会做出错误的修改。这才是注释的价值。

### 7.2 反例的归档

反例随时间过期，写在规范里会成为新的维护负担。本规范只保留判定标准；
三类典型反例（注释承诺与实现矛盾、测试注释超出实际断言、注释复述代码）
连同真实代码收在 HISTORY.md 的"注释反例"一节。

## 8. 落地与校验

### 8.1 落地节奏

- 新增文件立即遵守；其余文件按模块分批补齐，一个模块一次提交。
- 一次提交只做一类内容：注释、文案、文档不混合，这样 `git diff` 可以只按注释行过滤来审查。

### 8.2 校验项

| 检查项 | 方式 |
| --- | --- |
| 每个 `.h/.cpp` 有 `@file` 且路径存在 | CI 脚本 grep |
| §6.2 禁词表零命中（含 `docs/*.md` 与 README） | CI 脚本 grep |
| Markdown 相对链接可达 | CI 脚本 |
| 文档中的测试数与 `tests/CMakeLists.txt` 一致 | CI 脚本 |
| `@param` 名与签名一致 | 人工评审 |
| 注释描述与实现一致 | 人工评审 |

### 8.3 评审清单

- [ ] 新文件有 `@file`，内容与文件名一致
- [ ] 公共函数写了 `@param` 与 `@throws`（抛异常的函数）
- [ ] 没有复制事实源里的数字
- [ ] 没有无出处编号与历史叙事
- [ ] 链接点开过
