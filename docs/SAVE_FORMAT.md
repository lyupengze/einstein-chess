# 存档格式

本文说明 `einstein_save.db` 里一条存档的字段与编码。写入与读取的实现都在
`src/storage/save_manager.cpp`，本文与实现冲突时以实现为准；本文只描述格式，
不描述 SQL 语句的拼接方式。

## 1. 存储位置与表结构

- 数据库文件默认名 `einstein_save.db`，相对路径，实际位置取决于进程的当前工作目录
  （GUI 启动时切到可执行文件目录，CLI 跟随启动目录，可用 `--db` 指定）。
- 库里只有一张表 `saves`：

  ```sql
  CREATE TABLE IF NOT EXISTS saves (
      name      TEXT PRIMARY KEY,
      data      TEXT NOT NULL,
      timestamp DATETIME DEFAULT CURRENT_TIMESTAMP
  );
  ```

- 一个存档槽一行：`name` 既显示名也是主键，同名保存即覆盖；`timestamp` 由 SQLite 在写入时生成，
  列表按 `timestamp DESC, name ASC` 排序，同一秒内按名称升序。

## 2. 数据串布局

`data` 列是空格分隔的三行文本：

```text
第 1 行：7 个局面元数据
第 2 行：25 个棋盘格 + 1 个 AI 档位（共 26 个整数）
```

第一行以换行结束；第二行的 25 个格子之间以空格分隔，最后一个格子后紧跟档位数字，
档位后面是换行。解析按空白分词，因此行内空格数量不影响结果，但字段数量必须严格匹配。

## 3. 字段定义

第一行 7 个元数据，顺序固定：

| 序号 | 字段 | 取值 | 说明 |
| ---: | --- | --- | --- |
| 1 | `player1_side` | 0 / 1 / 2 | 发起方阵营；只能取红 1 或蓝 2，0 被拒绝 |
| 2 | `current_side` | 0 / 1 / 2 | 当前行棋方；含义随阶段变化，见第 5 节 |
| 3 | `phase` | 0~4 | 阶段：0 布阵、1 掷骰、2 Player1 思考、3 Player2 思考、4 终局 |
| 4 | `dice` | -1~6 | 本回合骰点；-1 表示无骰子，其余必须是 1~6 |
| 5 | `winner` | 0 / 1 / 2 | 胜者；非终局必须为 0 |
| 6 | `player1_ready` | 0 / 1 | 发起方是否已提交布阵 |
| 7 | `player2_ready` | 0 / 1 | 另一方是否已提交布阵 |

第二行先写 25 个格子（按第 4 节的顺序），最后写：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `ai_level` | 0 / 1 | 当局 AI 档位；0 随机档、1 搜索档，缺失或越界按损坏处理 |

## 4. 棋盘编码与顺序

- 每个格子是一个有符号整数：`+1..+6` 表示红方对应编号的棋子，`-1..-6` 表示蓝方对应编号的棋子，`0` 表示空格。
- 格子按 `x`（行）为外层、`y`（列）为内层遍历，从 `(0,0)` 到 `(4,4)`：
  前 5 个是第 0 行，接着 5 个是第 1 行，依此类推。
- 棋子编号保持正数语义，蓝方只通过负号区分；因此 `-0` 不是合法编码，读取端也不会产生它。

## 5. 写入前的校验

`save_game()` 在拼字符串之前依次检查，任何一项失败都不写库：

1. `ai_level` 必须属于 `ai::kAllLevels`，否则抛 `std::invalid_argument`；
2. `phase` 为 `LayOut` 时拒绝保存（布阵阶段没有可恢复的界面流程），抛 `std::invalid_argument`；
3. 整个局面交给 `core::validate_state` 校验，有问题抛 `std::runtime_error`，消息里带首个问题的字段名。

这样数据库里不会出现“写得进、读不回”的存档，同名覆盖也不会把好存档换成坏存档。

## 6. 读取与拒绝条件

读取端先做格式与转换安全检查，再由 `core::validate_state` 做领域一致性检查。以下情况全部按数据损坏拒绝，
不会退回默认值：

- 第一行不足 7 个整数，或 `ready` 字段不是 0/1；
- 棋盘格缺失，或绝对值大于 6；
- 第二行在 25 个格子之后缺少档位，或多出任何内容；
- 档位不是 0/1，或档位数字溢出 32 位整数（例如尾部写成 `999999999999999999999999999`）；
- 局面组合不自洽，例如阶段是思考却没有骰点、`current_side` 与阶段矛盾、棋盘上出现重复编号、
  终局记录的胜者与棋盘实际胜负条件不符；
- 局面处于布阵阶段。

最后一类由 `core::validate_state` 统一裁决，校验项清单见 [架构说明](ARCHITECTURE.md) 的状态机一节。

## 7. 示例

一局刚开始、双方已布阵、轮到红方掷骰的存档：

```text
1 1 1 -1 0 1 1
1 2 3 0 0 4 5 0 0 0 6 0 0 0 -6 0 0 0 -5 -4 0 0 -3 -2 -1 1
```

拆开看：

- 第一行：发起方红、当前红、阶段 1（掷骰）、无骰子、无胜者、双方已就绪；
- 第二行前 25 个数：红方 1~6 在左上初始区，蓝方 -1~-6 在右下初始区；
- 最后一个数 `1`：当局 AI 档位为搜索版。

## 8. 版本策略

格式没有 schema 版本号：字段数量、顺序或含义变化时，写入与读取必须同批修改，
并且不保留对缺字段数据的兼容。这样“读不出来”会在读档时以明确错误暴露，
不会静默退化成默认局面。
