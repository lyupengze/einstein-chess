# 存档格式

本文说明 `einstein_save.db` 里一条存档的字段与编码。写入与读取的实现都在
`src/storage/save_manager.cpp`，本文与实现冲突时以实现为准；本文只描述格式，
不描述 SQL 语句的拼接方式。

## 1. 存储位置与表结构

- 数据库文件默认名 `einstein_save.db`，相对路径，实际位置取决于进程的当前工作目录
  （GUI 启动时切到可执行文件目录，CLI 跟随启动目录，可用 `--db` 指定）。
- 库里只有一张表 `saves`：

  ```sql
  CREATE TABLE IF NOT EXISTS saves (
      name      TEXT PRIMARY KEY,
      data      TEXT NOT NULL,
      timestamp DATETIME DEFAULT CURRENT_TIMESTAMP
  );
  ```

- 一个存档槽一行：`name` 既显示名也是主键，同名保存即覆盖；`timestamp` 由 SQLite 在写入时生成，
  列表按 `timestamp DESC, name ASC` 排序，同一秒内按名称升序。

## 2. 数据串布局

`data` 列是空格分隔的两行文本，一行只装一类数据：

```text
第 1 行：标量头（字段见第 3 节）
第 2 行：棋盘格（顺序与数量见第 4 节）
```

第一行以换行结束；第二行以换行结束。解析按空白分词，行内空格数量不影响结果，
但两行的字段数量都必须严格匹配。

## 3. 字段定义

所有整数都必须整段匹配：不接受前导 `+`，含非数字字符、写成负数零（`-0`、`-00`）都按损坏拒绝。
其中元数据、棋盘格与 AI 档位按十进制 32 位有符号整数解析；随机种子按 32 位无符号整数
解析；已掷次数按 64 位无符号整数解析，另有上限见下。

第一行标量头的字段顺序固定：

| 序号 | 字段            | 取值      | 说明                                                         |
| ---: | --------------- | --------- | ------------------------------------------------------------ |
|    1 | `player1_side`  | 0 / 1 / 2 | 发起方阵营；只能取红 1 或蓝 2，0 被拒绝                      |
|    2 | `current_side`  | 0 / 1 / 2 | 当前行棋方；各阶段允许的取值见 [架构说明](ARCHITECTURE.md) 的状态机一节 |
|    3 | `phase`         | 0~4       | 阶段：0 布阵、1 掷骰、2 Player1 思考、3 Player2 思考、4 终局 |
|    4 | `dice`          | -1~6      | 本回合骰点；-1 表示无骰子，其余必须是 1~6                    |
|    5 | `winner`        | 0 / 1 / 2 | 胜者；非终局必须为 0                                         |
|    6 | `player1_ready` | 0 / 1     | 发起方是否已提交布阵                                         |
|    7 | `player2_ready` | 0 / 1     | 另一方是否已提交布阵                                         |
|    8 | `ai_level`      | 0 / 1     | 当局 AI 档位；0 随机档、1 搜索档，缺失或越界按损坏处理      |
|    9 | `seed`          | 0~4294967295 | 当局骰子随机源的种子；与 CLI 打印、`--seed` 是同一个值   |
|   10 | `rolls`         | 0~`core::kMaxRollCount` | 本局已掷骰次数；读档后从这一位置继续骰序        |

`rolls` 的上限是 `core::kMaxRollCount`：读档要按次数重放随机流（`mt19937::discard`），
没有上限时手改的超大值会让读档长时间占用 CPU。

第二行的格子含义与顺序见第 4 节；多一个少一个都按损坏拒绝。

## 4. 棋盘编码与顺序

- 每个格子是一个有符号整数：`+1..+6` 表示红方对应编号的棋子，`-1..-6` 表示蓝方对应编号的棋子，`0` 表示空格。
- 棋盘是 `core::Board::kSize` × `core::Board::kSize` 个格子，按 `x`（行）为外层、`y`（列）为内层遍历，
  从 `(0,0)` 到 `(4,4)`：同一行的格子相邻，行与行依次相接。
- 棋子编号保持正数语义，蓝方只通过负号区分；空格只有 `0` 一种写法，读取端拒绝 `-0`。

## 5. 写入前的校验

`save_game()` 在拼字符串之前依次检查，任何一项失败都不写库：

1. `ai_level` 必须属于 `ai::kAllLevels`，否则抛 `std::invalid_argument`；
2. `rng.rolls` 不能超过 `core::kMaxRollCount`，否则抛 `std::invalid_argument`；
3. `phase` 为 `LayOut` 时拒绝保存（布阵阶段没有可恢复的界面流程，读档端同样拒绝，见第 6 节），抛 `std::invalid_argument`；
4. 整个局面交给 `core::validate_state` 校验，有问题抛 `std::invalid_argument`，消息里带首个问题的字段名。

这样数据库里不会出现“写得进、读不回”的存档，同名覆盖也不会破坏原有存档。

## 6. 读取与拒绝条件

读取端先做格式与转换安全检查，再由 `core::validate_state` 做领域一致性检查。以下情况全部按数据损坏拒绝，
不会退回默认值：

- 第一行字段数量与第 3 节的表不同，或某个字段不是规范的整数（溢出、前导 `+`、`-0`）；
- `ready` 字段不是 0/1；
- 第一行在元数据之后缺少档位、随机种子或已掷次数；
- 档位不是规范的 32 位整数（溢出、`-0`），或不在 0/1；
- 随机种子不是规范的 32 位无符号整数（溢出、`-0`），或已掷次数不是规范的 64 位无符号整数；
- 已掷次数超过 `core::kMaxRollCount`；
- 第二行格子数量与第 2 节不同：缺失、多出，或某一格不是规范的 32 位整数（溢出、`-0`）、
  绝对值大于 6；
- 第二行之后还有多余内容；
- 局面组合不自洽，例如阶段是思考却没有骰点、`current_side` 与阶段矛盾、棋盘上出现重复编号、
  终局记录的胜者与棋盘实际胜负条件不符。

其中「局面组合不自洽」由 `core::validate_state` 统一裁决，校验项清单见
[架构说明](ARCHITECTURE.md) 的状态机一节；其余各项由 `deserialize()` 在解析字段时直接拒绝。

布阵阶段在两端都拒绝：`save_game()` 在写库前抛出，`deserialize()` 在 `validate_state` 通过后
按损坏数据拒绝。布阵阶段的就绪标志与骰点都没有可恢复的界面流程——GUI 与 CLI 的读档入口都直接
进入对局，没有回到布阵页的路径。

## 7. 示例

一局刚开始、双方已布阵、轮到红方掷骰的存档：

```text
1 1 1 -1 0 1 1 1 42 0
1 2 3 0 0 4 5 0 0 0 6 0 0 0 -6 0 0 0 -5 -4 0 0 -3 -2 -1
```

拆开看：

- 第一行的元数据：发起方红、当前红、阶段 1（掷骰）、无骰子、无胜者、双方已就绪；
- `ai_level` 为 `1`：当局 AI 档位为搜索档；
- `seed` 为 `42`：骰子随机源种子为 42，与 CLI 打印的种子是同一个值；
- `rolls` 为 `0`：本局还没有掷过骰子；
- 第二行：红方 1~6 在左上初始区，蓝方 -1~-6 在右下初始区。

## 8. 版本策略

格式没有 schema 版本号：字段数量、顺序或含义变化时，写入与读取必须同批修改，
并且不保留对缺字段数据的兼容。这样“读不出来”会在读档时以明确错误暴露，
不会静默退化成默认局面。

第一行最后三个字段（AI 档位、随机种子、已掷次数）都属于对局的一部分：档位决定对手强弱，
种子与已掷次数共同决定读档之后的骰序。三者都必填，缺失任何一个都按损坏拒绝，
不会用默认档位或新的随机流代替。
